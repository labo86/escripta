# Spec Writing Rules

## Goals

- Specs should be implementation-guiding, not aspirational notes.
- A developer should be able to start work without guessing missing details.

## Rules

- State the problem before proposing the solution.
- Separate goals from non-goals.
- Write acceptance criteria as observable outcomes.
- Call out constraints and compatibility concerns explicitly.
- Include a concrete test plan.
- Track open questions instead of burying uncertainty in prose.
- Update the spec when scope materially changes during implementation.

## Completion

A spec should move to `done/` only when:

- code is merged or otherwise finalized
- acceptance criteria are satisfied or explicitly deferred
- test status is recorded
